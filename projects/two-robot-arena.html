Two-Robot Arena

Two TETRIX robots, each with a Raspberry Pi and webcams, share a marked arena. One typed request, like bring the bottle to the near-left corner, becomes a plan: find the object, send the closer robot, and move the other one out of the way.

  • Raspberry Pi
  • TETRIX PRIZM
  • Arduino C++
  • Python
  • OpenCV
  • YOLO
  • ArUco
  • MCP
  • Multi-robot

The setup

  • Robots: TETRIX MAX chassis on a PRIZM controller (Arduino Uno-compatible), two encoder drive motors, an ultrasonic sensor, a line sensor and a servo claw.
  • On each robot: a Raspberry Pi with USB webcams. The PRIZM plugs into the Pi over USB.
  • Computer: runs YOLO on the robots' camera streams and coordinates the two robots.
  • Arena: 200 × 200 cm with eight printed ArUco markers near the corners and a virtual wall 20 cm inside the edge.

Where vision should run

The work started with a measurement rather than an assumption. I benchmarked object detection on the Pi against sending JPEG frames to a computer over Wi-Fi and over Ethernet, first with OpenCV colour detection and then with a pretrained YOLO26 nano model. Offloading to the computer also let a 32-bit Pi OS use YOLO without installing PyTorch. That became the camera pipeline: the Pi keeps only the newest frame from each webcam, the computer returns labels and boxes, and the Pi measures how old each result is when it arrives.

Robots that take goals, not motor commands

Each Pi runs a robot server that accepts intents such as drive, turn, find an object and approach it. Every intent is checked against a policy (speed and distance limits, a clear path by ultrasonic, battery and link state) before anything moves, and guards recheck obstacles, stalls and timeouts every 50 ms while it runs. Each one ends in a status record: succeeded, failed, cancelled or rejected, with the reason. The server speaks the Model Context Protocol (MCP), so a client like Claude Code can call it directly.

Two rules run through the design:

  • The Pi decides and the PRIZM executes. The PRIZM sketch only runs validated, numbered commands, streams telemetry 20 times a second, and brakes on its own if the Pi goes quiet for 400 ms.
  • Safety reactions happen on the robot, never over Wi-Fi. The computer handles heavy vision and planning.

Avoiding each other with cameras only

Each robot wears four ArUco markers, one per side. From a single marker in one frame, the other robot estimates distance, bearing and how squarely it is being faced. The rule is short: if we face each other, both sidestep right; otherwise, step away. In 20,000 simulated head-on meetings it ended too close 0.0% of the time with perfect sensing and 2.4% with pessimistic noise, against 10.8% and 11.1% for always step away. This rule has not been run on the robots yet.

The arena

Each robot works out its position and heading from the corner markers in view, and tracks it between sightings with the wheel encoders. On the computer, an arena server turns a request into steps for the two robots: it picks the closer one, moves the other aside if it is in the way, lets one robot drive at a time, and stops both if they come within 35 cm.

First run on the robots

On 15 November 2026, both robots drove and turned by command, both claws were calibrated, and each robot found its position from the corner markers. One complete task ran: fetch the bottle to the near-left corner finished in 57 s. Robot 1 found the bottle 67 cm away, robot 2 was moved out of the carrying path first, and robot 1 picked the bottle up, carried it and set it down.

Still being fixed before relying on it:

  • Robot 1 drove 55–57 cm when asked for 50 cm, so its wheel calibration needs redoing.
  • The cameras' focal length is not calibrated yet, so marker distances are approximate.
  • In that run, robot 2 could not reach the YOLO receiver on the computer, so it could not search.

Testing

The software for the arena phase passes 124 tests, and whole tasks run end to end against two simulated robots. The PRIZM sketches also compile for the PC against stub Arduino and PRIZM headers, so their command validation and watchdog can be tested without hardware. Passing tests show the code agrees with its simulators; the floor, motors and network are what the run days are for.
